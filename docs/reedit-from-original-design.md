# 从原图重复调整 — 设计定稿

- 日期：2026-10-02　分支：`gl-engine`　状态：待用户复核，未开工
- 术语按 `AGENTS.md`「术语约定」：**原图** = 用户从相册选的那张本身；**成品图** = 裁剪/缩放/挪位后上屏的那张；**缩略图** = 网格显示用的派生图。

## 1. 要解决的问题

今天点铅笔（`MainActivity.btn_edit` → `openEditItem` → `EditActivity` 重编模式）打开的是**成品图**（`EditActivity.java:91-93`），源文件是上一轮的裁剪结果。表现就是「裁上加裁」：取景框缩到最小也看不到被裁掉的画面，只能往更紧的方向调，且每轮再叠一次重采样。

用户真正要的是**微调**：成品图只是稍微高了一点/矮了一点，下次打开还能看到整张原图，并且**上次摆的位置原样复原**，手指拖一点点就够了。

## 2. 本期做什么 / 不做什么

做：留存原图；铅笔改为以原图为源；存一份裁剪矩形用于复原取景框；存量壁纸提供一次性「关联原图」入口；备份包带上原图。

不做（各自独立，将来要另开一期）：

- 成品图格式仍是**无损 PNG**，不改 JPEG/WebP（用户明确要求不丢清晰度）。
- 不做多版本构图（不能撤销回上一版构图）。
- 不改成「只存参数、上屏时实时裁」——那条要动 GL 纹理、锁屏 `setBitmap`、缩略图、小组件、通知封面五个消费点，与本期无关。
- 导出目录「同名不覆盖」的老毛病（`WallpaperExporter.java:88/101`，`createDocument` 不查重名 → 出现 `xxx (1).png`）不在本期处理。
- 带 EXIF 旋转的原图方向语义（见 §11 已知未处理）。

## 3. 文件布局

```
files/
  wallpapers/<id>.png   成品图（上屏用，格式不变）
  thumbs/<id>.jpg       缩略图（派生，逻辑不变）
  originals/<id>        【新增】原图原始字节，无扩展名，不转码不缩放
  inbox/<id>            编辑期间的临时副本（不变）
```

`originals/<id>` 沿用收件箱的「无扩展名 + 原始字节」习惯：读它的一方（`BitmapFactory` / `BitmapRegionDecoder`）都靠嗅探格式，不靠扩展名；避免为了猜扩展名再引入一次 MIME 判断。

关键改动在 `WallpaperStore.confirmImport`（:255-260）：原来「写完元数据后删除收件箱文件」改成**移动到 `originals/<id>`**。移动而不是复制，所以不额外占一次 IO，也不会让收件箱留下已经入库的孤儿文件。多张待编辑队列不受影响 —— `MainActivity.onResume:726-731` 靠 `pendingInbox()` 列目录推进队列，文件被搬走等于「这张处理完了」，语义与今天删除完全一致。

## 4. 元数据：`library.json` 每个条目新增 6 个可选字段

```json
{ "id":"...", "lib_id":"...", "title":"...",
  "src_w":4000, "src_h":3000,
  "crop_l":812.5, "crop_t":0.0, "crop_r":2412.5, "crop_b":2700.0 }
```

- `src_w/src_h` 与 `crop_*` **都在原图像素坐标系**里，即 `EditActivity.exportByRegion` 现在算出的那个 `Rect`（:205-209）用的是同一套坐标，不另立一套归一化约定 —— 少一次换算就少一处能错的地方。
- 含义：上次成品图是从原图的这块矩形导出的。上面这组数字就是「竖构图裁掉了左右各约 800 像素」，下次打开取景框落回这里。
- 「有没有参数」的判据写死一条：`src_w` 或 `src_h` 缺失或 ≤ 0 即视为**无参数**，`crop_*` 不去猜。
- 只有**源是原图**的那次保存才写这六个字段；源是成品图（存量、未关联）时不写，避免记下坐标意义不明的参数。
- 参数与当前原图尺寸对不上时（换过原图），**不单独做清除动作**：那次打开按默认构图，保存时自然用新原图的尺寸覆盖写回，一次编辑就自好了。
- 字段全部可选。`load()` 用 `optInt/optDouble` 带缺省读（照现有 `optString` 风格，:103-104），旧版本读到不认识的键直接忽略，因此**降级回滚安全**：装了旧 APK 不会崩、不会丢条目，只是没有「复原构图」这个能力。

`Item` 类相应加 6 个字段，`saveLibrary`（:713-722）写出去。

## 5. 点铅笔时可能遇到的四种情形

| 原图在不在 | 参数在不在 | 参数与原图尺寸对不对 | 打开时 | 屏幕上会看到 |
| :- | :- | :- | :-- | :-- |
| 在 | 在 | 对得上 | 源=原图，取景框摆回 `crop_*` | 整张原图，但取景框已经是我上次的构图；往上下拖一点就是微调 |
| 在 | 不在 | — | 源=原图，fit-cover 默认构图 | 整张原图铺满取景框，从零摆一次（新关联的存量壁纸就是这格） |
| 在 | 在 | 对不上（换过原图） | 源=新原图，默认构图 | 顶部提示「原图换过了，上次的位置已作废，请重摆构图」 |
| 不在 | — | — | 源=成品图（= 今天的行为） | 顶部提示条 + 「关联原图」按钮（见 §6） |

判定用**实际读到的原图像素**（`BitmapFactory` 只读文件头，`inJustDecodeBounds`，跟 `readOriginalBounds()` :99-105 同一招）跟 `src_w/src_h` 比，不用文件修改时间之类的间接信号。

## 6. 关联原图（只服务存量数据）

- 入口**只有编辑页那条提示上的一个按钮**。不加壁纸格的第四个键（`item_wallpaper.xml:53/63/74` 那排三个 48dp 键，格子宽只有约 196dp，余量只剩 20dp），也不在预览弹窗里加行。
- 点按钮 → `PickVisualMedia` 开相册 → 选中后把原始字节复制进 `originals/<id>` → **就地**在原图上重新解码并显示，默认构图，接着裁接着保存，不用退出重进。
- 关联成功后参数写不写？不写。历史成品图不知道自己是从原图哪块裁的，硬凑一个矩形会给出错误构图 —— 所以第一次必须手摆，提示语直接说明「关联后需要重摆一次构图」。
- 关联完就是表格里的第一格了，之后每次保存都自动带上参数。
- 用户不需要为新增壁纸做任何关联动作：`confirmImport` 起就自动留存原图。

### 6.1 这是临时功能，以后删的时候动这几处

用户定位：关联原图只为修存量老数据，新壁纸一律走 `confirmImport` 自动留存，用不到它 —— 以后会要求整条删掉。删的时候按这份清单走，别把永久功能一起带走：

删（只服务于关联）：

- `EditActivity`：`pickOriginalForLinking()`、`onOriginalPicked()`、`linkOriginalLauncher` 字段与那两行注册、`noticeLinkButton` 字段/绑定/`setOnClickListener`
- `WallpaperStore`：`linkOriginal(...)`
- `activity_edit.xml`：`btn_link_original` 那一个 TextView（`edit_notice_bar` 与 `tv_edit_notice` 留着）
- `strings.xml`：`edit_link_original`、`link_original_failed`

留着（服务永久功能，跟关联无关）：

- `originals/` 留存、裁剪矩形六个字段、`CropView.restoreSourceRect`、`hasOriginal`、备份包里的 `originals/`
- 提示条本身与 `edit_notice_original_changed`：那是「换过原图后参数作废」的说明，不是关联的兜底
- `chooseSource()` 第 4 格与 `edit_notice_no_original` 那句话：删了按钮之后它退化成一句只读说明「这张没有原图，现在是在成品图上调整」，仍然有用；要更狠也可以整条删掉，但别把 `chooseSource()` 的源判定删成「找不到原图就崩」

## 7. `CropView` 要加的能力

现在只有 `setBitmap()` → `resetLayout()` 走 fit-cover 居中（:88-108）。新增一个方法：

```java
/** 按「位图坐标下的可见矩形」复原取景框：等价于用户自己捏到那个位置。 */
public void restoreSourceRect(RectF rectInBitmap)
```

实现要点：

1. 复用 `resetLayout()` 先算出 `minScale/maxScale`（否则 `matrixReady` 与钳制区间都是空的，会出现「捏合钳死在 1 倍」那种静默失效，:32-36 那条注释就是前车之鉴）。
2. `scale = viewW / rect.width()`；这块矩形本来就是从同一个满屏取景框里截出来的，`rect.height()/rect.width()` 理论上等于 `viewH/viewW`，所以**只按宽轴算比例**，高轴的微小偏差（浮点取整、屏幕密度变动）交给下一步的 `clampTranslate()` 吸收，不做第二套比例约定。
3. `matrix.setScale(scale)` 后 `postTranslate(-rect.left*scale, -rect.top*scale)`，让矩形的左上角落在取景框左上角。
4. 调用时机：`EditActivity` 后台解码回来后，把原图坐标的 `crop_*` 按现成的 `kx/ky`（:203-204）换算成**解码位图坐标**再传进来 —— 位图可能因像素预算被降采样过，直接用原图坐标会偏。
5. `scale` 若落在 `[minScale, maxScale]` 之外（极窄矩形 + 换过屏幕尺寸等），钳回区间再平移，绝不越界露黑边。

## 8. 保存路径

`EditActivity.onConfirm`（:149-182）基本不动，加两件事：

- 导出成功后（区域解码或兜底都算），若本次源是原图，把这次的可见矩形换算成**原图坐标**连同 `src_w/src_h` 一起写进该条目。
- 之后仍走原来的 `overwrite` → `Switcher.reapplyIfCurrent`（:165-174），成品图覆盖同一张、**id 不变**，所以槽位、定时、暂停标记、所属库、标题全部不受影响。

顺带一个真实的质量改善：微调后是从**原图原生像素**重导成品图，而不是在上一轮已缩放过的成品图上再裁再缩，少一次重采样。

「源是原图」在两种模式下都算：**导入模式**的源文件是 `inbox/<id>`，它本身就是原图（保存后搬进 `originals/`，尺寸一致），所以第一次导入也写参数 —— 新壁纸存完立刻点铅笔就能复原刚摆好的构图，不存在「刚入库的要先重摆一次」的空窗。只有存量老数据才有那个一次性的重摆。

## 9. 删除 / 备份 / 还原

- 删除壁纸：`deleteFullFiles`（:562-566）旁边加删 `originals/<id>`；条目没了，参数随 `library.json` 一起消失。
- 备份：`BackupStore.backup` 在现有两圈（:122-127）之外多打包 `originals/`，`BackupResult` 与 `manifest.json` 加一个 `originals` 计数，界面文案跟着显示第三个数。
- 还原：按 `originals/` 里的名字写回同名文件；**老包没有这个目录就跳过，不算失败**（否则今天的包一还原就报错）。沿用既有的「还原只增不删图片文件」约束。
- 还原后若包里参数指向的原图缺失（比如包是在别处备份的、或图被手工删了），落回表格第四格：提示未关联，可以给按钮补。

## 10. 体积与发热账（按验收原则「只减不增」）

- 磁盘：每张新增一份原图字节（JPEG 常见几百 KB～2MB）。成品图仍是 PNG，所以是**净增**。
- 发热/内存：**不动上屏链路**，桌面引擎与锁屏读的还是同一份 PNG，解码次数、重绘时机、WorkManager 排定一个字都没改 → 与今天持平。唯一新增开销是编辑页多解码一次原图（今天也要解码，只是文件从成品图换成原图），以及保存时多一次 `library.json` 原子写。

## 11. 已知未处理

- **EXIF 旋转**：`BitmapFactory` 解码会按 EXIF 转正，而导出走的 `BitmapRegionDecoder` 按编码后的原始像素坐标解释区域（:653-674）。本期沿用现成坐标系，因此**不会新增方向问题，也不会修掉既有那条差异**。真机上如果哪天发现「带旋转信息的原图，成品图方向不对」，那是既有行为，单独一期修。
- **HEIF 原图**：`decodeCropSource` 能解能显示，但 `BitmapRegionDecoder` 不支持区域解码 → 导出走现成兜底 `cropView.export(maxDim)`（`EditActivity.java:150-153`），清晰度略低于 JPEG 原图路径。参数照常有效（矩形语义与原图坐标无关）。
- 壁纸被删了但导出目录里的副本留着 —— 今天就这样，本期不动。

## 12. 验收用例（真机手工，无 adb）

1. 新相册选一张竖构图 → 裁 → 保存 → 卸载前先看 `备份` 包里的 `originals/` 计数应等于壁纸张数。
2. 点铅笔：应看到**整张原图**（被裁掉的左右两边都在），且取景框就停在刚才的构图上；手指往上拖约 60 像素保存 → 预览弹窗看成品图，构图应只挪了约 60 像素，而不是回到居中默认态。
3. 第 2 步之后再点铅笔：位置应是第 2 步结束时的构图（验证参数被覆盖写入）。
4. 找一张 v3.84 之前入库的老壁纸点铅笔：看到「未保存对应的原图」提示 + 按钮 → 关联同一张相册图 → 默认构图打开 → 摆一次保存 → 再点铅笔应能复原。
5. 存量壁纸关联原图时**故意选另一张图**（尺寸与原成品图不同）：应默认构图打开 → 摆一次保存 → 再点铅笔位置就是这次摆的（参数已被新原图尺寸覆盖写回）。然后再关联第三张尺寸不同的图 → 应提示「原图换过了，位置已作废，请重摆构图」。
6. 用第 5 步这种「参数与原图尺寸不符」的现场去设桌面/锁屏壁纸：上屏应与成品图文件一致，绝不能因为参数错乱而显示另一块区域（参数只影响编辑页取景，不参与上屏）。
7. 备份 → 卸载重装 → 还原：重复调整能力应保持（原图在包里）。
8. 老包（v3.84 之前备份的）还原：不应报错，缺原图的条目走第 4 条的提示路径。
