# 壁纸管理服务（账号 + 云端库 + 后端选图）实施方案

- **状态**：设计定稿，未开工。一行代码未动，版本号未升。
- **为什么不叫 sync**：本模型里服务端是唯一权威，客户端只是它的一份缓存，没有"两份副本合并"这回事。历史上"多设备同步"这个词会让人去找冲突合并算法，那是错的方向。
- **日期**：2026-10-07

**Goal:** 一个管理壁纸的服务端（账号、图、元数据、配额、选下一张）+ 一个负责切换的客户端（执行上屏、缓存、上报自己的缓存清单）。同一账号在多台机上登录，看到同一个库、同一份配额、同一套启用状态；**不保证**两台机同一时刻切到同一张。

**Architecture:** 服务端三张脸分职责看 —— **授权**（token 签发与配额判定）、**数据**（壁纸条目、库、取景参数、桶对象）、**选图**（按库与范围从"启用 ∩ 本机已缓存"里取下一张，无状态读）。客户端不做任何跨设备合并。字节的传输走 S3 协议的预签名 URL，**不过应用服务器**。

**Tech Stack:** 客户端仍是 Java 17 + 纯 JDK（`HttpURLConnection`，沿用 `UpdateChecker` 那几行的写法，零新依赖）；服务端 Java + 自托管 RustFS（Apache-2.0，S3 兼容），endpoint / bucket / region / 凭证一律可配置，将来换 OSS 或 R2 只改配置。

## 2. 服务端数据模型（只列契约，DDL 落服务端仓库）

- **user**：id、创建时间、档位（免费/会员）、档位到期时间、状态。密码只在服务端存 Argon2id；客户端**只见 token**，不碰密码。
- **device**：id、user_id、名称、App 版本、最后在线时间、**缓存清单的摘要版本**（用于判断要不要让设备重报）。设备数配额在这里判。
- **wallpaper**：id（沿用客户端 UUID，`WallpaperStore.java:141` 已是稳定 id，可直接当主键）、user_id、库 id、标题、取景参数（`src_w/src_h/crop_*`，一律**原图像素坐标**）、`in_rotation`（启用与否，见 §7 关于命名的那条）、字节数、原图 sha256、上传状态、最近上屏时间（给到期降级挑"留哪几张"用）。
- **library**：id、user_id、名称、覆盖范围（桌面/锁屏）、mode（顺序/随机）、interval_seconds。库数配额在这里判。
- **upload_ticket / download_ticket**：一次性、短时效，服务端签发，绑 user_id。日志里不许记录完整 URL（带签名参数，等于凭据）。

原图的对象 key：`users/<user_id>/originals/<wallpaper_id>`。**内容寻址的 sha256 只做校验，不做去重**（去重会引入跨用户引用，是合规与删除链路的双重坑）。

## 3. 接口清单（全部 HTTPS，全部带 device token）

| 动作 | 语义 | 幂等性 |
| :-- | :-- | :-- |
| `POST /pair` | 用配对码换 token（单租户阶段：旧机屏上出码、新机扫，复用现成二维码视觉） | 否；配对码一次性 |
| `GET /state?device=` | 全量拉条目 + 库 + 配额 + 档位 | 是 |
| `POST /cache/report` | 上报本机缓存集（首登全量，之后增量） | 是，按清单版本号 |
| `POST /upload/request` → `PUT` 预签名 → `POST /upload/commit` | 三步上传，commit 时服务端判配额并落 sha256 | commit 按 (wallpaper_id, sha256) 幂等 |
| `GET /next?lib=&scope=&device=` | 从 启用 ∩ 本机已缓存 里按该库 mode 取下一张 | 否，但服务端记游标，重复调不跳两张 |
| `POST /queue/refill` | 预取队列补一批（默认 20 张 id） | 是，按队列版本 |
| `POST /quota/probe` | 客户端上传前问一句"我还能启用几张" | 是 |

失败一律回**带语义的错误码**：`quota_walls`、`quota_devices`、`quota_libs`、`tier_expired`、`token_expired`、`cache_empty`、`storage_full`、`bucket_unreachable`。客户端文案表按这些码一一对，见 §8。

## 6. 磁盘、发热与流量这笔账

**发热**：新增只有三块 —— 首登那次全量下载 + 重编成品图/缩略图的 CPU、预取队列每次补批的一次 HTTPS 往返、上传时的一次读盘与 sha256。**定时唤醒链路一行网络代码都不加**，这条是硬约束，也是本方案对 `AGENTS.md` 那条"新功能要交只减不增的发热账"的回答：稳态下唤醒只读本地，比现状（打包整库、手动搬运）不多一次唤醒。

**下行**：按 `lan-sync-plan.md` §2 那行示例折算，每张壁纸三件合计约 16MB（原图占大头，约 7~8MB）；只传原图后每台新机的首次下行从 600MB 量级降到 250~450MB 量级。**这是示例数，自己的真数见 §10 待填。**

**磁盘**：启用集全常驻，不做 LRU —— 淘汰是合法操作（选图集合是 启用 ∩ 本机已缓存），但淘汰后那张在**这台机**上不再被选中，直到重新拉回。界面上要让用户看见"已启用、未在本机"这一档，不能只显示一个灰色缩略图。

**存储**：停用与淘汰都不减少桶里的字节。囤积的治理靠 RustFS 的 Lifecycle/ILM 把长期停用的原图降到低频层，另配一个很宽的用户级字节上限兜极端；RustFS 的 Bucket Quota 是**桶级不是用户级**，每用户占用要自己累计。

**熔断**：私桶 + 短时效签名 URL + 单用户当日下行上限（超限即停并如实报 `cache_empty`/`bucket_unreachable` 类的具体那一种）+ 用量告警。四条都是配置项，阈值写方案时按机器带宽现算，不抄网上的数。

## 7. 配额与到期降级

额度一律**服务端判**，客户端只做显示与入口拦截；本地判的配额重装就绕过。

| 轴 | 免费 | 会员 | 拦截点 | 有成本依据吗 |
| :-- | :-- | :-- | :-- | :-- |
| 启用张数 | 5（**账号级，非每库**） | 不限 | `POST /upload/commit` 与置启用时 | 有：下行与本机磁盘 |
| 设备数 | 1 | 3 | `device` 计数 | 有：每台新机一次预拉 |
| 间隔下限 | ≥ 现值 900 秒 | 放开到 60 秒 | `LibraryStore.java:45` 那个常量与 `:266`/`TimerScheduler.java:91` 两处 `Math.max` | 没有，反而减服务器成本；卖的是唤醒频率=他的电 |
| 库数 | 1 | 5 起 | 建库入口 + 槽位选库 | 没有，纯产品维度；转化最直观（映射到刚做完的选库页与翻面槽位） |

按库算额度会留套利洞（10 个库 × 5 张 = 白送 50 张），所以是账号级。免费给 1 个库意味着"桌面一套图、锁屏另一套图"变成会员权益 —— 这条是刻意的，那正是本 App 的独特能力。

到期降级三拍：① 默认保留"最近 30 天上屏过的 N 张"（靠 `wallpaper.最近上屏时间`），并给一次可点的改留提示；② 正在上屏那张若落在停用集里，**只影响下一次切换**，不撤下，锁屏也撤不下来（系统里存的是位图副本）；③ 超额的库置为"未接入槽位"，原先指向它的槽位退回第一个仍在免费档的库，库与其下的图全部保留。停用/停库不删任何东西是硬规矩。

**不许复用 `LibraryStore.java:181` 那个 `enabled` 字段做降级停库** —— 它是 v3.60 槽位化为降级回滚刻意保留的遗留字段（仅 JSON 往返、无人读）。一旦开始读它，就要同时确认还原路径与旧版本 APK 遇到 `enabled=false` 会不会当它不存在继续切。给降级停库单独一个键。

新机的空缓存：首登后缓存集为空，后端没有可选集 → 现象会是"装了新机壁纸死活不换也不说为什么"。规则：首登按启用集在 Wi-Fi 下排队预拉，拉到 1 张才允许上屏，没拉够时如实报 `cache_empty` 给界面与小组件 —— 与 `Switcher.java:24-26` 的"如实报 `engine_inactive`、不做任何切换"同一口径。

## 8. 失败场景与文案（不许出现"出错了"）

| 场景 | 错误码 | 界面给的话 |
| :-- | :-- | :-- |
| 免费档还想多启用 | `quota_walls` | 「免费档同时参与切换的是 5 张，你已经存了 N 张 —— 停用几张，或开会员不限张数（停用的图不会删）」 |
| 会员到期 | `tier_expired` | 「会员已于 X 到期，N 张已停用、仍在你的库里，恢复会员就继续用；这 5 张我按最近上屏的给你留着了」 |
| 第 2 台机登录 | `quota_devices` | 「这台机是第 2 台，免费档只接 1 台：在旧机上登出，或开会员接 3 台」 |
| 第 2 个库 | `quota_libs` | 「桌面和锁屏各配一套图是会员功能，免费档只有 1 个库」 |
| 间隔想设到 15 分钟以内 | `quota_libs` 之外单独判 | 「免费档最快 15 分钟切一张；会员可以设到 1 分钟（越密越费电）」 |
| 新机还没拉到图 | `cache_empty` | 「这台机的库还是空的：正在 Wi-Fi 下取第 1 张，取到就能切」 |
| 服务器挂了 | `bucket_unreachable` | 「连不上图库：已缓存的这些照旧照常切换，只是暂时不能新增和改库」 |
| 上传半途断 | — | 「传到一半断了，已丢掉重来一次（不做断点续传，与局域网那条同一个取舍）」 |
| 桶里字节超宽上限 | `storage_full` | 「你的图库已存到 N GB 的上限，会员可扩到 M GB；停用几张不会腾地方（原图要留着随时重编）」 |

## 9. 施工顺序

1. 阶段 A：**只改数据层，不碰网络**。`Item.in_rotation` 进 `library.json`（读侧 `optInt("in_rotation", 1)` —— 老包与老数据一律按启用，前向兼容写死不许靠猜）、间隔下限抽成一个档位表、`check.cmd` 跑过。这一阶段单独发版就有收益（停用功能本身用户要得到），且为后面留好了地基。
2. 阶段 B：服务端最小可用 + 单租户配对码 + `GET /state` + 全量拉取，客户端仍本地选图（先把库和取景搬到云上，选图不动）。
3. 阶段 C：原图上传三步流 + 预签名 PUT + 缓存清单上报 + 服务端选图与预取队列 + `TimerScheduler` 只读队列。
4. 阶段 D：配额判定、到期降级、熔断与告警、档位下发到界面。
5. 阶段 E：真机验收（§10）后才谈开放注册与收款。

## 10. 验证状态

**已核过（有据）**：`WallpaperStore.java:62/78-79/83-102/141/826-847`、`Switcher.java:17-18/22-26/36/113/167/255/334`、`LibraryStore.java:45/80/181/266/344`、`TimerScheduler.java:91/177`、`MotionPlayer.java:230`、`LibPickerActivity.java:239`（成品图尺寸由本机屏幕算出、原图是再编辑唯一源、实况段在原图尾部、暂停与上一张是运行时）；Muzei 的远程图必先落本地文件（`MuzeiArtProvider` 的 `cacheDir`/`filesDir` 分界、100 张 LRU 只删文件留行、`DirectBootCache` 连解锁前都要留一份）；RustFS 能力表（Apache-2.0、1.0.1、S3 Core/Versioning/Lifecycle/IAM/Bucket Quota 标 ✅）与 SNSD 不能原地扩容那条限制；MinIO 为 AGPL-3.0 且 OSS 版最后提交 2026-04-24。

**没核过，开工前必须验**：① RustFS 的**预签名 PUT** —— README 能力表没单列，装起来第一件事就是打一发（客户端侧 `HttpURLConnection` 上传必须 `setFixedLengthStreamingMode(file.length())`，否则会走 chunked 而 presigned PUT 要求 Content-Length，症状伪装成"密钥配错了"）；② 荣耀手机在 4G/家用网络下对候选机房的**可达性与实测吞吐**（`lan-sync-plan.md` §10 那五个数还待填，本方案要再加三个：首登下行耗时、重编 N 张成品图的耗时与温升、单次补队列的往返毫秒）；③ 阿里云/R2 的现行单价（上一轮那两个数来自整理文，官方页是 JS 没抓到）；④ 国内云的备案与内容合规要求原文；⑤ 荣耀应用市场对虚拟商品计费的现行规定；⑥ 收款主体（个体户还是公司）—— 这条不定，§7 那张表的"会员"就只能做成兑换码。

## 11. 本版刻意不做

- **跨设备合并算法**：服务端权威，没有合并。
- **成品图/缩略图上云**：由本机屏幕算出的派生物，各机自己编。
- **断点续传**：与局域网那版同一个取舍。
- **唤醒链路联网**：不许以任何理由加回来。
- **跨用户内容去重**：合规与删除链路的坑，不做。
- **本地判配额**：绕过成本为零。
- **后台自动同步**：只在手动动作与 Wi-Fi/充电的预取队列补拉里发生。
